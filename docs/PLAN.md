# Listenly implementation handoff

Updated 28 September 2026. This is the single implementation brief and work order; it replaces the earlier roadmap. Supporting contracts and evidence are linked below.

## Goal and completion gate

**Deliver one trustworthy learner journey: choose a reviewed test → sign in → check audio → answer and recover saved work → submit once → understand mistakes through recording evidence → reopen the same result from History.** Keep the current UI foundation and existing serverless services.

Portfolio-ready means this entire journey works live with one reviewed four-part, 40-question test. Independent practice additionally needs useful part-level review, honest attempt labels, and selectable one-part practice. A build, generated recording, or attractive screen does not satisfy either gate.

## What the completed investigation established

- **Observed:** library, Admin preview, sound-check controls, keyboard answer entry, review marking, and answer recovery worked. Refresh preserved two QA answers and a mark, but restarted reading time and reset paused playback from 0:27 to 0:00.
- **Observed blocker:** live submission and retry both failed with a generic test-service error; History showed no completed result. The local Decimal patch exists, but its deployment and the current server exception were not verified. Diagnose before choosing a fix.
- **Observed:** the local login loop cleared after the QA server received normal outbound access to Cognito signing keys. This does not establish that all login problems are resolved; verification errors currently become silent redirects.
- **Observed:** the only published Portfolio QA Mock repeats hotel/transport material across parts. It is demonstration content. At a narrow measured viewport, word-limit labels and save status disappeared. Practice still imposed a timed final review.
- **Source risks:** browser/backend marking disagree; saves lack conditional concurrency protection; attempts read mutable current content; evidence editing can discard timing; progress mixes conditions. See [Architecture](ARCHITECTURE.md#known-limitations-from-the-review).
- **Unverified:** successful live Results/replay, cross-device consistency, a realistic uninterrupted mock, registration/recovery/logout flows, real-phone accessibility, and editorial accuracy of all content. Prior passing checks are historical, not current end-to-end proof. No learner interviews were performed.

## Implementation status

All eight tasks now have a local implementation, but none is live-verified and the overall journey is not complete. The backend and API-route changes are not deployed. The only available published test is still demo material; no editorial approval was invented.

1. **Submission and login reliability — locally implemented, live diagnosis blocked.** The local submission path stores band values as DynamoDB-compatible `Decimal`, returns a durable completed result on retries, logs unexpected backend failures with a sanitized request reference, preserves the requested destination, and distinguishes an unreachable verification service from invalid credentials. The prior live generic 500 cannot be attributed conclusively without deployed logs/artifact evidence. Local browser QA verified the destination and verification-service message, including at 390×844; no learner credentials were available for a protected submit flow.
2. **Authoritative marking — locally implemented.** Submission now stores per-question outcomes and server-owned part/type breakdowns. Browser Results consumes those outcomes instead of remarking answers. Shared backend fixtures cover punctuation, hyphenated word counts, number allowance, word limits, multi-selection partial credit and one-part totals. Reviewed answer fixtures and editorial sign-off remain unavailable.
3. **Attempt concurrency — locally implemented.** Attempts carry revisions; saves and submission use conditional writes; submission names the exact saved revision; consistent reads, duplicate submission and lost-response recovery preserve completion. Focused tests reject stale writes and a revision changed before submission. Cross-device behavior is not deployed or live-tested.
4. **Immutable releases — locally implemented; editorial gate blocked.** Publishing creates an immutable release record, learner attempts pin it, archived/edited source records do not change the pinned result, and Admin distinguishes demo from reviewed content with required reviewer/date/provenance fields. Every saved edit advances the content version; publication conditionally advances the source pointer only from the validated version; and a retry can finish updating the source record if the matching immutable release write already succeeded. Existing audio references are retained. A reviewed 40-question release and deployment are still required.
5. **Mock/practice behavior — locally implemented; signed-in device QA remains.** Learner timing consumes the published audio plan; mock Part transitions continue automatically; practice final review is untimed; practice playback position is saved and restored after refresh; interruptions and assistance are recorded; narrow save/error and word-limit text remains visible; dialogs move and contain keyboard focus, close with Escape and restore focus; and the unrelated map fallback was removed. Real-browser fixture QA covered the 390×844 practice-review, dialog and audio-failure paths, an automatic mock transition, and practice recovery at the saved timestamp. Signed-in real-device checks with reviewed protected audio remain blocked by credentials, reviewed content and deployment.
6. **Review — locally implemented; content verification blocked.** Results shows original instructions, choices and visuals, server outcomes, accepted answers, explanations, optional transcript evidence, passage replay with whole-Part fallback, expired-audio refresh and release-bound question reports. Admin preserves and edits replay timing; Admin and backend validate timing order and recording duration. Every question and actual replay still need editorial review on a reviewed release.
7. **One-Part practice — locally implemented.** `/practice` offers a complete Part selector, attempts store the selected Part, scoring/review uses its actual mark count, and no practice band is returned. Protected browser completion/reopen remains unverified.
8. **Home/History/Progress honesty — locally implemented.** Attempts label first/repeat exposure, mode, interruptions, assistance and demo status; Progress includes only first, uninterrupted, unassisted reviewed full mocks; History paginates retained attempts and uses pinned titles/counts; network/save states and signed-audio refresh are explicit. Live pagination and recovery remain unverified.

## Settled defaults and work to avoid

Use raw scores first; no band for demo content or one-part practice. Consider clearly approximate bands only for reviewed full mocks. Practice feedback follows a complete part; mock answers remain hidden until submission. Browse/sample before account creation is the preferred later access flow. Keep History reopening exact reviews before building a separate saved-mistakes collection.

After the core gate, observe five IELTS learners choosing, finishing, recovering, reviewing and returning; then run a small return-use trial. Prepare a second distinct reviewed test before claiming useful unseen follow-up practice. Neither establishes learning gains or calibrated difficulty.

Defer chatbots, AI diagnosis, streaks/badges, reminders, compulsory diagnostics, elaborate dashboards, bulk generation, pricing work and infrastructure rewrites. Do not repeat the broad research. Recheck only the task's current source/runtime evidence. Follow [implementation guidelines](IMPLEMENTATION_GUIDELINES.md); documentation is not authorization for deployment, paid generation, account changes or Git publishing. Report each task as implemented, locally verified, live verified, or blocked with exact evidence. Do not mark the overall goal complete while the live journey or editorial gate is missing.
